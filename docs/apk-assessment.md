# APK assessment before conversion

After **Add game** selects an APK, PocketMicro assesses it in the background and
shows **APK assessment and suggested fixes**. The screen gives a suggested path,
rule-level reasons and known limitations. It offers a review action and **All
conversion options**; selecting a suggestion still opens the existing conversion
confirmation. An experimental candidate opens the explicit experiment warning.
No installation or APK modification occurs during assessment.

Recommendations are based on inspected structure and actual supported rules:

- **Startup repairs** when an existing catalog repair, stale TEXTREL declaration
  repair, or supported OUYA cleanup form applies.
- **Experimental Unity candidate** when the separate read-only proxy/payload
  inspection matches the restricted ARM-only experiment. No transformed bytes
  are generated by this inspection. It does not establish successful gameplay.
- **Standard conversion** when no supported startup fix matched. This is not an
  all-clear; runtime faults, service dependencies and incomplete evidence remain.
- **No recommended conversion fix** for proven device minSdk/ABI mismatches,
  invalid DEX or resource-only/incomplete game packages. Findings retain their
  unsupported, malformed, unknown and skipped distinctions.

The checker does not infer a working purchase/input fix from engine names or
string markers. A supported nullable CPU getter is reported as a pattern; its
runtime failure is unverified by the scan and its guard remains coupled to an
eligible explicit experiment. PocketMicro never changes a game's purchase checks.

Every PocketMicro installation preparation path now requests on-screen controls
automatically: suggested/standard conversion, manual conversion,
startup repairs, the explicit Unity experiment and the APK doctor (including its
exported APK). The duplicate touch-only menu variants and touch checkboxes have
been removed. All app paths use `ApkRebuilder.prepareForInstall`; low-level
explicit APIs retain their previous behavior for inspection and tests.

The existing input patcher checks the launch activity and reports the selected
native/fallback route or why controls were skipped. Unsupported/protected DEX is
preserved; automatic attempts do not prove input response. The experiment composes touch hooks after the CPU guard. Reconvert the complete
original APK to add controls to an already installed native-only conversion.
Doctor copies prepared before this policy must be prepared again before export
or installation; a versioned readiness marker prevents reuse of stale copies.

The APK doctor includes the same recommendation. Its ordinary **Prepare fixes**
does not select experiments; an experimental finding tells the user to use Add
game to review that option. The Android install target used by both ordinary and
experimental Add game conversion now follows the same phone-specific policy as
the assessment/doctor: API23 floor through Android34, API24 on Android35/36.
Higher original targets are preserved. Post-36 policy remains unknown.

## Bounds and evidence

A private temporary copy is limited to 2 GiB and deleted on success or failure.
The input document stays unchanged. ZIP entry names/counts and duplicate entries
are checked. Native scanning is limited to 128 files, 24 MiB per file and 64 MiB
aggregate; DEX inspection to 64 files, 32 MiB per file and 64 MiB aggregate.
Skipped data is reported. Eligibility is checked again during conversion, so a
document changed after assessment cannot bypass the repair rules. The existing
catalog preview may construct transient output copies to verify known plans;
those copies are never installed or written over the original by assessment.
Game classes, native code and managed assemblies are not executed by the scan.

Regression tests cover standard, exact-catalog, stale-declaration, SDK cleanup
and experimental suggestions; ABI/minSdk limits; API floors; malformed/missing
content; uncertain/Thumb candidates; read-only previews and input preservation.
On the full supplied Monocle APK, the checker selects the experimental candidate
with original bytes unchanged and no experimental output generated. A private
native-15 fixture selects the existing catalog path. New generated checks and all
host suites pass, along with Android-core Java compilation. Existing native replay
still verifies 12 available profiles and skips five unavailable fixtures with a
nonzero incomplete result; missing fixtures never count as passes. No device UI
or Android installation test has been executed for this feature.
